## Auto-layout

`cargo test -p processcraft-core --test layout --locked --offline` covers deterministic repeated preview, a branch/join, cycle and self-loop, one pool with lane and unlaned nodes, labels and explicit styles, event/gateway border endpoints, malformed/missing/duplicate DI and cancellation, proposal tampering, exact session apply/no-op/undo/redo, 400 nodes, and a 500-edge proposal without mutating the source. Tests are fixture-scoped; they do not establish all BPMN structures or imports.

The layout is a layered (Sugiyama-style) pipeline in `layout.rs`. Layering: DFS back edges, longest path, then each source pulled next to its nearest successor; weakly connected components are laid out separately and stacked inside each band, and unconnected nodes are packed into a square grid. Every forward edge gets one dummy vertex per layer it crosses (at most 20,000 vertices, else `budget`); a long edge between lanes runs on dummies in its source lane, unless moving them to its target lane lowers the score (layer crossings plus the vertices back edges must pass to reach their channels), tried once per such edge (one greedy pass, skipped when the number of such edges times the layered vertex count exceeds 200,000). Ordering: four rounds of barycenter down/up sweeps plus one adjacent-transposition pass, all inside fixed (lane, component) groups (lane order never changes; no node leaves its lane), keeping the order with the fewest crossings. Rows: two median passes (predecessors, then successors) fitted to strictly increasing integer rows, so a split, its upper branch and the join share a row and long edges run on their dummy row. Coordinates: per-column width and per-row height from the node and its external label; the gap after a layer is max(60, 24 + 8 per vertical leg); with a pool, lanes start at the pool's 30 px header. Routing: each forward edge leaves its port, changes rows on its own 8 px track in the inter-layer gap and enters the target port. In a gap, upward legs sit left of downward ones; upward legs that start higher run further left and downward legs that start higher further right, so legs whose spans do not nest never cross. Of the forward flows that could leave an event or gateway through its top or bottom vertex, only the one whose partner lies farthest that way takes it, and a vertex under the node's external label is never used; the others take the side. Several flows on one side of any node spread along it (left/right sides by partner y, the flow nearest the centre row keeping the centre so straight runs stay straight; top/bottom by descending partner x), with ports on the outline (rectangle, diamond, ellipse); back edges use the top or bottom channel of their component block, and an endpoint blocked on that side leaves through its side port and a gap track. A route with more than 16 points or one crossing a node falls back to the obstacle router, then to a plain gap route; nothing is refused for routing. Edge labels take the first spot (above or below the longest horizontal segments, then right of vertical ones) clear of nodes and placed labels.

Measured (release, `cargo test --release -p processcraft-core --test layout -- --nocapture`): the 400-node / 500-edge connected fixture (399-edge chain plus 101 skip edges) now returns a proposal in 5.8 ms with 0 crossings and no warnings; the whole layout test binary runs in 0.03 s. New property tests assert validation, determinism, no node overlap, nodes inside their lanes, lanes at pool x + 30 and orthogonal routes of at most 16 points: a diamond with crossed IDs, a two-lane ping-pong chain, a loop inside a branch, two disconnected components (disjoint y extents) all have 0 crossings, and a back edge blocked above and below is laid out. Loop/nested and newly modelled BPMN kinds remain fixture-scoped evidence.

Crossing repair (2026-11-14): a 48-node, 59-flow commercial litigation matter over five lanes (no pool; two loops, an event-based gateway, an inclusive split/join, flows jumping lanes both ways), laid out through the CLI (`run`, `layout-preview`, `layout-apply`, `export-image`), went from 6 crossings and 8 overlaps (warnings: 8 route segments over a label, 9 sharing a channel, 6 crossings) to 1 crossing, 0 overlaps and 0 shared channels; bends rose from 59 to 67 and the area by 1.4 %. Causes found: legs in one gap were stacked in the wrong order (every pair of overlapping downward or upward legs crossed), gateways shared one side between several flows or routed through their own label, and long inter-lane edges always ran in their source lane (so the "Revise" loop and a gateway branch had to cross them). The remaining crossing is forced by the fixed lane order: the path start, intake, conflict check, "no conflict", engagement runs left to right through the Client and Risk lanes, "Waiver granted?" lies below it in the Partner lane and "Send declination letter" above it in the Client lane, so any left-to-right route between them crosses that path once. `litigation_matter_over_five_lanes_has_one_forced_crossing` rebuilds the same graph (modeler sizes, 90 x 40 labels under events and gateways) and asserts the property helper, 1 crossing, 0 overlaps and no other warning. Release: the 400-node / 500-edge fixture still returns in 5.6 ms with 0 crossings (single sample, same machine); the layout test binary runs in 0.02 s.

The proposal is best-effort: `LayoutProposal` carries `warnings` (one `{code, message}` per code: `label_overlap`, `route_over_label`, `route_over_node`, `shared_channel`, `crossings`, the message giving the count) and `metrics` (`crossings`, `overlaps`, `bends`, `edge_length`, `area`). Both default when absent, so earlier proposal files still read; `validate_proposal` still compares only the proposed geometry. The final pairwise check is no longer charged to the routing budget; it is bounded by the 400-shape / 500-edge / 16-waypoint limits. The desktop preview bar appends the crossing and warning counts (hover lists the messages), `layout-preview` reports the warning count and metrics, and MCP `layoutPreview` returns them in the proposal. Tests: impossible long labels now yield a proposal with a `label_overlap` warning; a K3,3 between three exclusive gateways and three tasks returns `metrics.crossings >= 1` with a `crossings` warning and passes `validate_proposal`; the ordinary-process cases assert no warnings.

The node profile is an exclusion list: text annotations, data object and data store references, boundary events (kind or boundary details) and events attached to an activity are refused, as are subprocesses, ad-hoc subprocesses and transactions whose shape is expanded. Every other flow node is accepted with its details: all task kinds, call activities, collapsed subprocesses, intermediate events and all gateway kinds. All activities use the rectangular port placement. The single process/pool, data, I/O specification, message-flow and sequence-only gates are unchanged. Tests: a service task, intermediate catch event, inclusive gateway and collapsed subprocess chain is laid out and validates (it currently carries one `route_over_node` warning); a boundary event and an expanded subprocess are refused with `unsupported` without changing the document.

One batch, one undo step; refusals leave content, history, and generation unchanged.

## Modeling parity phase 4: direct manipulation (post-M3)

Core (`manipulate.rs`, `geometry.rs`, re-implemented from the bpmn-js/diagram-js move, resize, snapping, attach/detach, drop-on-flow, and reconnect behavior), exposed as four new mutations shared by the GUI, CLI batches, and MCP (`moveElements`, `resizeShape`, `reconnect`, `createAt`), each one batch and one undo step:

- Boundary events follow their host: `geometry::prepare_move` adds every attached boundary event shown in the diagram (keeping its relative place on the outline, also on resize), so its label moves and its flows are re-docked by the existing route repair. A boundary event moved without its host (arrow keys, align) may only slide along the host border band (15 px either side of the outline); otherwise the move is refused.
- Resize rules: `resizeShape` accepts only `rules::can_resize` elements (expanded subprocess 140x120, lane 300x60, pool 300x150, group 140x120, text annotation 100 wide, east/west only), refuses going below the minimum or cutting off contained shapes (20 px padding: subprocess content, pool process nodes, lane members), moves attached boundary events with the outline, and re-docks connected edge ends proportionally. Contained shapes do not move.
- Snapping: `geometry::snap` matches the moved shape's mid, top-left, and bottom-right to the same points of other shapes (and mids of connected ones) per axis within a tolerance; the GUI uses 7 screen px and draws full-width guide lines. Alt or Ctrl moves freely. View > "Snap to 10 px grid" (off by default) snaps the centre to the grid on axes without an element match.
- Attach/detach: a single moved intermediate catch event (message/timer/signal/conditional) or blank throw event whose centre lands on an activity's border band becomes a boundary event of it (`rules::can_attach`, same scope required); a boundary event dragged off its host becomes an intermediate catch event, or a throw event without a definition, unless `can_drop` keeps it attached (error, escalation, compensation, cancel, non-interrupting). Definitions are kept through the replace machinery (`replace::set_attachment`), and flows the rules no longer allow are deleted. The GUI outlines the host while dragging.
- Drop on flow: a single moved or created flow node (not a boundary event) whose centre is within 5 units of a sequence flow of its scope, and that can be connected from the flow's source and to its target, splits it: the flow keeps its ID, condition, and default marker and now ends at the node; a new sequence flow runs to the old target; both are routed with the preferred layouts; a flow duplicating an existing connection is not created (or, on the incoming side, removed). The GUI highlights the flow while hovering. `SpliceActivity` is kept for existing callers.
- Bendpoints: a selected edge shows waypoint and segment-middle handles. Dragging a waypoint moves it, dragging an orthogonal segment moves it across its axis (end points slide with it), a diagonal segment gets a new bendpoint; double-click removes an interior bendpoint (all through `reroute`). Dragging an end onto another shape runs `reconnect`: same flow ID, `can_connect` re-checked, refused when the pair needs another flow kind, another scope, or would duplicate a connection, when the flow is shown in more than one diagram; a changed source drops its default-flow marker.
- Drag-create: the main palette entries can be dragged onto the canvas (rectangular ghost plus the attach/flow feedback); `createAt` places the element in the scope and lane under the point, attaches intermediate events dropped on an activity border, refuses a boundary event dropped elsewhere, and inserts into a flow. A click still uses append/auto-place.
- Containers: moved flow nodes join the lane under their centre (`assignLane`). A single flow node dropped into another expanded subprocess or pool changes scope only when it has no flows, data associations, or boundary events; otherwise the move is refused with the reason.

Tests: `crates/processcraft-core/tests/manipulate.rs` (boundary follow and border slide/refusal, resize refusals and children kept in place, snapping candidates, attach then host move then detach with undo, drop-on-flow split by move and by create with one undo step and lane assignment, reconnect allowed/refused/duplicate, lane membership and clean scope change vs refusal); GUI unit tests for resize handles and route editing; headless egui tests dragging a task with its boundary event and dropping a task on a flow. Gates on Windows 11: fmt, workspace Clippy with `-D warnings`, and `cargo test --workspace --all-targets --all-features --locked --offline --no-fail-fast` (1082 passed, 0 failed).

Limits: attach, drop on flow, and scope change apply to single-element moves only (multi-element moves update lanes only); message flows are not split; snapping considers every non-dragged shape that does not contain the moved one, not only siblings; dragging an edge end onto empty canvas cancels; the drag-create ghost is a plain rectangle and the "More BPMN elements" menu entries are click-only; route-repair warnings from `prepare_move` are not reported for drags through `moveElements`; resizing a pool does not resize its lanes (phase 5).

## Modeling parity phase 5: pools, lanes, containers (post-M3)

Core: `containers.rs` re-implements the bpmn-js lane handlers, auto-resize, create-participant, toggle-collapse, and diagram-js space tool behavior (not copied). Five new mutations are shared by the GUI, CLI batches, and MCP (`addLane`, `splitLane`, `createPool`, `toggleCollapse`, `makeSpace`); each is one batch and one undo step, and refusals leave content, history, and generation unchanged.

- Lanes (horizontal): `addLane` above/below a lane or pool adds a 120 high lane at the 30 px indentation; for a lane, everything in the pool past a line 10 px inside the lane's edge moves 120 away and the pool and parent lanes grow (the target lane and its children stay); for a pool, only the pool grows, and a pool without lanes first gets one lane covering its body. `splitLane` (2-10) divides a lane or pool evenly (rounded, the last lane takes the remainder) and reuses existing child lanes in vertical order; more existing lanes than requested is refused. `resizeShape` on a lane or pool applies bpmn-js `computeLanesResize`: all lanes of the pool take the change across the lanes, and lanes sharing the moved edge (within 10, or 5 for the same edge) follow it; a follower squeezed below its minimum refuses the resize. Deleting a lane lets its siblings take its space (all of it at an edge, half from each side in the middle). Lane membership follows the geometry after every lane operation, pool/lane resize, auto-resize, and space step: a flow node whose lane under its centre changed (or that had no lane) joins the innermost lane now under its centre; the model keeps one lane per node.
- Auto-resize: after `createAt`, `append` (the GUI append now goes through the mutation), `moveElements`, and expanding, a pool or expanded subprocess whose border the elements come within 2 (top/bottom) or 15 (left/right) of, or pass, grows to 60/100 beyond them, recursively up through outer containers, in the same batch. Pools grow through the lane rule above, so edge lanes follow. Lanes and pools never trigger it, plane diagrams are not resized, and resizes still refuse to cut off children (20 px padding).
- `createPool`: in a process diagram the diagram becomes a collaboration diagram and the pool takes the process; when the process already has shapes the pool wraps them (content box + 20 padding + 30 header, at least 600x250, body centred on the content). In a collaboration diagram the pool gets a new empty process and is placed at `center` (default: below the diagram's shapes). The GUI "Pool" palette entry uses it.
- `toggleCollapse` (also offered as "Collapsed subprocess"/"Expanded subprocess" and the ad-hoc variants in the replace menu; `replaceElement` routes these targets to it): collapsing shrinks the subprocess to 100x80 around its centre and moves its content's DI (nodes, lanes, flows, groups, data associations, ports at any depth) into the subprocess's own diagram (plane = the subprocess, created when missing), placed at 180,160 as in bpmn-js; expanding moves that content back centred on the subprocess, sizes it to max(350x200, content and itself) centred on them, and auto-resizes its container. Boundary events keep their place on the outline and edges are re-docked.
- `makeSpace` (space tool): shapes wholly past the line move by the delta (or those before it with `before`), resizable shapes crossing it grow or shrink (text annotations excluded), boundary events follow their hosts, edges between affected shapes keep the points before the line and shift the rest, edges with one affected end are re-docked. Removing more space than a container's minimum allows is refused.

GUI: the context pad of a selected horizontal lane or pool (with a process) offers add lane above, add lane below, divide into two lanes, and divide into three lanes; the pad stays inside the canvas, so shapes wider than the view keep a reachable pad. S (or View > "Space tool (S)") toggles the space tool; a canvas drag shows the line and the swept band and applies `makeSpace` on release along the dominant axis (Ctrl moves the shapes before the line); Escape leaves the tool.

Tests: `crates/processcraft-core/tests/containers.rs` (wrap on create pool and a second pool with its own process; add lane below a lane with shifted shapes, re-docked edge and kept membership; add lane above a pool; first lane plus new lane on a pool without lanes; split into three with members moving to the middle lane, refusal, pool split reusing lanes; lane resize moving the shared edge and switching membership, refusal below the neighbour's minimum; pool resize carrying its lanes; delete at an edge and in the middle; auto-resize right and bottom through moves and createAt with one-step undo, no cut-off; collapse via the replace option and expand back with undo; space tool insert, edge shifting and re-docking, refusal) and a headless egui test clicking "Add lane below" on a new pool's context pad. Gates on Windows 11: fmt, workspace Clippy with `-D warnings`, and `cargo test --workspace --all-targets --all-features --locked --offline --no-fail-fast` (1092 passed, 0 failed).

Limits: adding and splitting vertical lanes is refused (resize and delete handle both orientations); the space tool always considers the whole diagram (bpmn-js limits it to the hovered pool unless a modifier is held) and edges with one affected end are re-docked rather than re-laid-out; deleting a lane does not delete its child lanes; collapsing does not create an empty subprocess diagram when the subprocess has no content shapes; lane membership is single-lane (a parent lane does not also list its child lanes' nodes); pool creation takes the plane process only when no pool references it yet.

## Modeling parity: deferred core items closed (post-M3)

Core rules and builders (`rules.rs`, `modeling.rs`, `geometry.rs`, `manipulate.rs`, `replace.rs`, `containers.rs`, `clipboard.rs`, `commands.rs`), shared by GUI, CLI batches, and MCP:

- Compensation associations: `can_connect` returns `CompensationAssociation` for a compensation boundary event to an activity in its scope (not its host, not an event subprocess), checked before the sequence-flow rules as in bpmn-js. `connect` creates an association with `associationDirection="One"`, sets the target's `isForCompensation`, and removes what that no longer allows (the target's sequence flows and boundary events, the event's previous compensation association). The core invariant accepts a boundary-event -> activity association; it routes like a sequence flow out of a boundary event; `reconnect` keeps it.
- Self-loops: a flow node connects to itself by sequence flow when the sequence rules allow it as source and target. New loops use the bpmn-js loop layout b:l (`RouteLayout::Loop`, 20 px segments); a re-layout keeps the side of the first waypoint (t:r, r:b, b:l, l:t). A moved shape translates its loops.
- Message flows from or to interaction nodes nested in subprocesses of a pool are allowed; the invariant resolves the pool through the subprocess chain to the root process. BPMN export/import round-trips them.
- Associations: an annotation may connect to an element in any scope (the association lives in the annotation's scope; BPMN association refs are any BaseElement) and to a pool or a collaboration-level annotation (a collaboration artifact association), but not to its own container. `rules::locate` now finds collaboration text annotations. The core invariant and the IO import accept association ends in any scope.
- Vertical layouts: under a vertical pool or lane (`isHorizontal=false`, innermost containing pool/lane) auto-place goes south (learned gap along y, minimum distance 90, boundary offsets left/right, annotations and data references on the vertical bpmn-js spots) and routes use `geometry::layout_route_vertical` (the horizontal layout on transposed geometry, so h/v swap and loops turn counter-clockwise). `addLane`/`splitLane` work in vertical pools (lanes stack along x, the 30 px indentation is on y; "above"/"below" mean left/right).
- Replace re-lays out the sequence and message flows of a replaced element whose size class changes (associations and data associations keep their re-docked interior points). Flows into or out of an expanded subprocess use h:h (or v:v when vertically apart), as bpmn-js does.
- Moves: every top-level moved flow node (not in another moved subprocess, and only when neither its old nor its new container moves along) changes scope when dropped into another expanded subprocess or pool, also in multi-selection moves; its boundary events go with it. Its flows are kept and moved to the scope that now owns them, converted sequence -> message flow when it now crosses pools (no condition) and message -> sequence flow when both ends are now in one scope (no message), and otherwise deleted; converted flows are laid out again. Data associations still refuse a scope change. Attach/detach and drop-on-flow stay single-element gestures.
- Drop on flow also splits message flows: the part keeping the flow's kind keeps its ID and the other part gets the kind the rules pick (e.g. message flow into a receive task dropped in the target pool, then a sequence flow on to the old target). bpmn-js `canInsert` would refuse this (the message flow's parent is the collaboration); ProcessCraft allows it when both parts are valid connections.
- Route repair: when kept bendpoints cannot be repaired around obstacles (e.g. a fresh duplicate moved over its original), `prepare_move` lays the sequence flow out again instead of refusing, and reports it. `ChangeSet.warnings` carries route warnings from `moveElements`, `align`, and `distribute`; the GUI controller shows them as a notice.
- Lanes: deleting a lane deletes its child lanes at any depth (siblings take the space, members follow the geometry). Collapsing a subprocess without content creates its empty subprocess diagram. `makeSpace` takes the drag start `at`; inside a pool only that pool and the shapes in it take part (the whole diagram otherwise); the GUI passes the drag start.
- Clipboard: copies pools with their whole process (lanes included), groups, the data object behind a copied data object reference, data associations whose owner and data reference are copied, and message flows whose ends are copied. QName references (`{namespace, local}`) are remapped only in the document's own namespace; a data association's `owner` is remapped (a node's `owner` text is not). Pasted flow nodes join the lane under them. `default_scope` picks the paste target scope for a diagram.
- New commands `align` (`shape_ids`, `alignment`), `distribute` (`shape_ids`, `distribution`), and `duplicate` (`element_ids`, `dx`, `dy`, optional `target_diagram_id`) expose arrange and copy/paste to `processcraft-cli run --batch` and MCP; `processcraft-cli run --help` lists the compound commands.
- `createFlow` keeps a scope's sequence flows before its associations, the order BPMN export writes them, so exported files re-import to the same model (an association followed by a sequence flow made export refuse before).

## Modeling parity: connection route quality (post-M3)

Core only (`geometry.rs`, `modeling.rs`, `manipulate.rs`, `commands.rs`); every entry point (GUI, CLI batches, MCP) reaches it through `reroute`.

- Route normalization: the `reroute` command passes its waypoints through `geometry::tidy`, which straightens a segment within 2 units of horizontal or vertical by moving its interior end onto the other end's axis (one pass from the start, one from the end), then drops duplicate and collinear points (`compact`). Endpoints never move; routes with fewer than three points or with out-of-range coordinates are stored as given. An explicit edge label is shifted by the delta of the route's midpoint (`geometry::midpoint`, half the polyline length), so labels follow moves, resizes, reconnects and manual edits. `prepare_move` still emits its absolute `setLabelBounds` for translated nested routes (auto-layout reads it); applied after the reroute it sets the same bounds. `modeling::edge_ends` resolves the two shapes of any edge kind (flows, collaboration and process associations, data associations; an explicit DI source/target wins, a data port without a shape resolves to its activity), and `resizeShape` uses it, so data associations are re-docked on resize too. Tests: `tests/geometry.rs` (`reroute_tidies_the_route_and_its_label_follows`); updated expectations: the repaired routes in `prepared_move_repairs_connected_edge_in_one_undo` and `prepared_group_move_keeps_manual_bends_and_undoes_together` no longer double back over the kept bends, kept bends left collinear are checked to lie on the route instead of being listed, and moved edges' labels now follow the midpoint.
- Outline docking: after normalization `reroute` docks each endpoint that lies on its shape's border band (`on_border`, 15 units inside or outside the bounding box) on the shape's true outline (`geometry::outline_point`: ellipse for events, diamond for gateways, rectangle otherwise). A horizontal or vertical end segment is projected along its axis, so it stays orthogonal; a diagonal end moves radially. An end segment running along a side (or missing the shape) and endpoints outside the band, such as deliberately detached imported routes, are kept. Test: `tests/geometry.rs` (`reroute_docks_ends_on_the_true_outline`: an off-centre vertical end at an event's bounding-box bottom lands on the circle; ray/outline intersections for rectangle, diamond and ellipse). Limits: data object folds and data store arcs dock on their bounding box; on shapes smaller than 30 units the band covers the whole interior, so an endpoint placed inside such a shape is docked too.
- Re-docking on move and resize: `geometry::redock_side` keeps a moved endpoint when its neighbour (the next kept waypoint, or the other end's shape centre on a two-point route) still lies beyond the side it is on, and otherwise moves it to the middle of the side facing the neighbour (the dominant axis when diagonal). `prepare_move` applies it to translated endpoints on their shape's border band before the route repair (`repair_owned_endpoints` derives the exit stub from the new side and keeps the interior bendpoints), and `redock` (resize) applies it after the proportional scaling. When kept bendpoints cannot be repaired, the sequence-flow fallback now uses `modeling::route` on the diagram as it will be after the move (gateway, boundary and vertical-pool layouts) instead of the horizontal layout. Tests: `tests/geometry.rs` (`moved_end_redocks_on_the_side_facing_its_neighbour`: a task moved above the bend column re-docks from its left side onto its bottom and keeps the interior bend), `tests/manipulate.rs` (`resize_redocks_data_associations`). Updated expectations in `moving_event_or_gateway_keeps_route_outside_endpoint_owners_and_undoes`: an event moved below its bend column now leaves from its top, so the bend the old route doubled back to is dropped (only the bend next to the unmoved end is asserted), and the "unproven endpoint" case uses an endpoint 40 units off the border, since one 1 unit off is now re-docked rather than refused. Limit: `modeling::route` still searches a single corridor.
- Straight associations and one routing entry point: `modeling::route_between` (the `can_connect` rule check plus `route`) is the single entry point for new and rerouted connections; `connect` and the GUI "Reroute" action both use it, the GUI for any edge kind with ends resolved by `edge_ends` (the GUI-only `connection_route` wrapper is gone, and a refused pair shows the rule's reason). As in bpmn-js, plain associations and data associations are laid out straight: two points, each the `outline_point` of its shape toward the other shape's centre; compensation associations stay orthogonal. `prepare_move` crops a moved two-point association or data association again on both outlines instead of bending it through `repair_endpoints`. Tests: `tests/modeling.rs` (`new_association_is_straight_between_both_outlines`); updated expectations in `tests/geometry.rs`: the moved data association ends in `valid_data_association_endpoints_move_undo_and_redo`, `global_data_store_association_moves_and_restores_route` and `moving_activity_translates_visible_port_and_repairs_association` now lie on the moved shape's outline toward the other end (e.g. `(54, 7.0625)` instead of the translated `(54, 8)`) rather than being translated. Limits: orthogonal associations already stored in a file keep their route until rerouted; an association with more than two points is still repaired with its bends; a rerouted imported association between elements the rules do not connect (e.g. task to task) is refused with the rule's reason.
- Edge rendering (`processcraft-render/src/bpmn.rs`): every edge (sequence and message flows, associations, data associations) is now one path per visible run instead of one subpath per segment. `polyline_path` rounds each corner with a quadratic curve of radius `min(5, half of each adjacent segment)`; `stroke_polyline` strokes it 1.5 wide with round joins and dashes it with `tiny_skia::StrokeDash` (message 7/7, association and data association 2/2), so the pattern runs continuously around corners instead of restarting per segment. The viewport builder clips each segment as before (`clip_segment`) and `clipped_runs` starts a new path only where clipping breaks continuity, with the dash phase set to the route distance at the run's start so dashes do not shift when panning. The scene is shared by raster, SVG and PDF output, so all three draw the same rounded polyline. The manual dash loops are gone: `dashed_lines` (dashed shape outlines such as groups and event subprocesses) uses the same continuous dash with sharp corners. Arrowheads and source markers still use the raw waypoints (`last_segment`), unaffected by the corner rounding. The previous protection is kept: a line needing more than 100 000 dashes is refused ("Dashed edge exceeds complexity limit"), and `many_dashed_edges_fit_path_budget` still passes unchanged. Test: `tests/bpmn_scene.rs` (`bent_sequence_flow_is_one_path_with_rounded_corners`: a three-point sequence flow yields one stroked contour plus its arrowhead). Checked visually on the procurement sample exported as PNG. Not run: `scripts/check_di_render.py` (Pillow is not installed on this machine); its PDF/PNG comparisons are self-consistency checks of one export, so they are expected to hold. Limit: conversation links keep their per-segment double lines.

### Resize (post-M3)

- Every shape resizes (`rules::can_resize`, which now always returns a `MinSize` with `keep_aspect` instead of `east_west_only`): activities of every kind and collapsed subprocesses (a shape without `isExpanded` counts as collapsed) down to 60 x 40, text annotations to 50 x 30 in both directions, events to 24 x 24 and gateways to 30 x 30, data stores to 24 x 24 and data objects to 24 wide at their default 36:50 ratio; pools, lanes, groups and expanded subprocesses keep their minimums. `manipulate::resize` refuses a locked-proportion size more than 1 unit off the shape's current ratio ("This element keeps its proportions"), keeps a boundary event's centre (the size changes around it, so it stays on the host's border), and for events, gateways and data references emits `setLabelBounds` so the external label stays horizontally centred below the shape with its gap and size unchanged. The space tool still stretches only containers (pools, lanes, groups, expanded subprocesses). The GUI keeps its four corner handles and, for locked kinds, scales the dragged rectangle to the shape's ratio from the opposite corner. Event markers, gateway glyphs and the data object fold already scale with `min(width, height)` in the renderer, and hit-testing uses the shape bounds. Tests: `rules.rs` (resize table), `tests/manipulate.rs` (`resize_follows_the_rules_and_never_cuts_off_children`, which previously asserted that a task "keeps its size", now resizes a task, refuses one below 60 wide, refuses a non-proportional event and checks the centred label; `a_resized_boundary_event_keeps_its_centre_on_the_border`), `canvas.rs` (`resize_moves_only_the_dragged_corner_and_keeps_a_minimum`: the east/west handle case is replaced by a locked-ratio case). - Resize gesture (GUI, `canvas.rs`): `resize_handles` gives eight handles (corners and edge midpoints) for free shapes and four corners for locked-proportion kinds; the nearest handle within 9 px is picked, filled on hover, and shows the matching resize cursor on hover and while dragging. `resize_bounds` returns whole units; `Shift` locks the ratio for any shape, `Alt` resizes symmetrically around the centre, `Ctrl` turns snapping off (as `Alt`/`Ctrl` mean "free" for moves, but `Alt` is taken by the centre resize here). The preview is clamped to the rule minimum and to the extent of the shapes the core checks (`manipulate::children`, now public, fully inside the old bounds, plus the now public `CHILD_PADDING`), so it never shows a size the core refuses for those reasons. Only the dragged corner or edge snaps: `snap_drag` (now taking the moved box) is called with an empty box at the dragged corner, so it reuses the move's sibling and connected candidates, guide lines and the optional 10 px grid; locked ratios do not snap. The gesture keeps its start in model coordinates, so auto-scroll (now also active for resize) and wheel panning mid-drag do not skew it. Test: `resize_moves_only_the_dragged_corner_and_keeps_a_minimum` (edge handle changes one axis, rounding, Shift ratio, Alt centre, clamp to contained shapes). Test: `fit_to_content_grows_a_long_name_and_keeps_the_minimum`. ### Manual edge editing (post-M3)

- GUI (`canvas.rs`): the bendpoint gesture records the bounds of the edge's two end shapes (`modeling::edge_ends`, so data associations too). `edit_route` drags an interior corner together with its two adjacent segments, so an orthogonal route stays orthogonal; dragging the first or last segment (or a corner next to an end) slides that endpoint along its shape's border, clamped to the shape's extent, instead of detaching it; with "Snap to 10 px grid" the moved coordinate rounds to 10. An endpoint dragged on or within 12 screen px of its own shape re-docks there (`end_dock` and `redock_end`, previewed live with a dot on the outline and the re-routed path, persisted as one `reroute`): the side is the one nearest the pointer (any side), the point along it follows the pointer, snapped within 7 screen px to the side's middle, the neighbouring waypoint or the far end, and is placed on the true outline by `geometry::side_point` (rectangle, ellipse for events, diamond for gateways; curved outlines keep to the inner 80% of a side). An interior neighbour beyond the new side follows along the end segment's axis or gains an elbow; otherwise the end leaves through a 20 px stub and the bounded `geometry::route` joins it to the neighbour (or to a stub off the far shape on a two-point route) around the end shapes. Hovering any edge handle shows a grab cursor, and edge handles take priority over the shape under them. Previously a release just outside the shape was a no-op and the preview moved the end freely; the earlier fix only re-docked on the bounding box nearest the pointer. Moving the shape later keeps the end's offset on its side while that side faces the neighbour (`prepare_move` translates the end, `redock_side` keeps it). Released on empty canvas away from the shape, the end stays where it was (it used to detach, which is how data-association ends got detached). Handle pick radius 6 to 8 px (drag and double-click). While connecting, a valid target previews the real route from `modeling::route_between`; otherwise the dashed centre-to-pointer line stays. Everything persistent is still a `reroute` or `reconnect` through the controller, so the core's `tidy` and outline docking apply. Tests: `bendpoint_and_segment_drags_edit_the_route` (corner drag stays orthogonal, end segment clamped on the border, grid rounding, re-dock with a following neighbour, side-middle snap, a stub around the shape, a two-point route re-docked on another side), `dragging_an_edge_end_docks_it_on_another_side_of_its_shape` and `an_end_slid_along_its_side_keeps_its_place_when_the_shape_moves` (GUI drags; one undo step, orthogonal route), core `side_point_docks_on_any_side_of_the_outline`. Limits: a drop on another shape reconnects with the core's docking, not the point under the pointer; on an event or gateway, an end near a 45-degree point may be re-centred on a side by a later move because `side_of` uses the bounding box; the stub route only avoids the two end shapes.
- Core: `manipulate::reconnect` first keeps the interior bendpoints, docking the changed end on the new shape's border facing its neighbour (straight across when level with a side, else mid-side) through `geometry::repair_endpoints`, and falls back to `modeling::route` when the repair warns (an end segment through either end shape or a non-orthogonal path) or the route has only two points. Test: `tests/manipulate.rs` (`reconnect_keeps_the_interior_bendpoints`). Limits: the kept bends are only checked against the two end shapes, so a kept route may cross other shapes, as a manual route can; the GUI end-segment slide uses the bounding box, the core re-docks it on the true outline.

## End-to-end CLI modeling check and vendor attributes (post-M3, 2026-11-12)

Three processes were built and checked through `processcraft-cli` only: an onboarding process (createAt/append chain, exclusive gateway with two branches, rework loop, replace Task → ServiceTask, createPool wrapping content, addLane in a second run), an order-fulfilment process (parallel split/join, business rule task, timer catch event, data object with a data output association, text annotation), and a Camunda Modeler style file (two pools, message flows, lanes, timer boundary event, data store with a bpmn.io `__targetRef_placeholder` association, `camunda:` and `modeler:` attributes, no `BPMNLabel`). All three validate, export BPMN that passes the pinned OMG XSD (`scripts/check_bpmn20_xsd.py`), and re-import as editable; the Camunda file round-trips byte-identically through export → import → export.

Defects found and fixed: data object references created by `createAt` or the palette had no backing `dataObject` and could not be exported; data association edges did not name their visible shapes (export refused activity-port ends); unprefixed QName references such as `attachedToRef="Task_1"` were treated as external, so imported boundary events were not drawn (an unprefixed name now resolves locally only when an element has that ID); backward sequence flows overlapped forward flows (they now run below and enter the target's bottom); new external labels clipped two-word names (90×40 now); an appended annotation's name did not become its text; replacing an element with its own type gave a misleading message. The desktop app now opens a `.processcraft` file or imports a `.bpmn`/`.xml` given on its command line.

Vendor attributes no longer block structural edits (solution design §6.2, widened): `has_opaque_xml` is unchanged for in-place rewrites, while the structural gate uses `blocks_structural_edits`, which ignores foreign attributes but not unmodeled extension elements or processing instructions. A batch that removes an element whose XML ID appears in a foreign attribute value is refused (`reject_removed_foreign_attribute_targets`). Test: `crates/processcraft-io/tests/extension_attributes.rs`.

Not changed: unmodeled `extensionElements` content (e.g. `camunda:inputOutput`) still blocks structural edits; default text annotations stay 100×30, so longer text is clipped with an ellipsis until resized.

Gates on Windows 11: fmt, workspace Clippy with `-D warnings`, `cargo test --workspace --all-targets --all-features --locked --offline --no-fail-fast` (1128 passed, 0 failed).
