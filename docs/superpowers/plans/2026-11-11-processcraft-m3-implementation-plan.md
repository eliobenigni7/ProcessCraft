# ProcessCraft M3 implementation plan

**Goal:** Deliver local analysis/review tools and extend the workbench to complete BPMN 2.0.2 modeling/interchange coverage, with explicit evidence per normative requirement.

**Architecture:** Rust, native Craft egui, one core mutation/history engine, bounded ZIP/JSON packages and the shared glyph scene. GUI, CLI and attached MCP use the same commands and file grants. The user explicitly expanded M3 beyond the earlier flat BPMN profile. A workflow execution server is outside the analyst workbench scope; executable-model metadata remains part of modeling/interchange coverage.

**Sources:** OMG BPMN 2.0.2 normative PDF, XSD and CMOF listed at https://www.omg.org/spec/BPMN/2.0.2. Schema declarations alone do not establish behavioral or semantic conformance.

## Partial delivery checkpoint

**Status (November 11, 2026): in progress.** The user has resumed implementation. The original review/export tools and first BPMN expansion waves are implemented; the complete BPMN modeling/interchange target remains unfinished. Do not mark M3 complete until the gates below are satisfied.

- Delivered: explicit bounded auto-layout preview/cancel/apply, comments with orphan handling, schema-3 named checkpoints/reference/frozen views, paginated detailed comparison and guarded restore, shared-scene outlined PDF export, shared CLI/MCP commands and broader typed BPMN profiles.
- Qualified: workspace regression, formatting and Clippy, focused official-schema XML round trips, native review/export checks and resource/checkpoint limit experiments; see [evidence](../../implementation/m3-evidence.md) for exact build scope and limitations.
- Remaining: the unchecked full-coverage work packages below, complete UI/property/DI parity, normative semantic validation and independent external-tool interoperability. The [normative gap crosswalk](../../research/bpmn-2-conformance-gap.md) identifies why the current implementation does not satisfy full process/choreography modeling coverage.

## Delivery order and parallel ownership

1. **M3.0 Auto-layout:** execute the existing [detailed plan](2026-11-11-processcraft-m3-auto-layout.md). A pure bounded deterministic proposal, explicit preview, cancel, stale-safe apply, exact one-step undo/redo and no-op detection. Initial auto-layout coverage remains explicitly narrower than the final BPMN editor; unsupported structures refuse without change.
2. **M3.1 Comments:** plaintext comments with stable IDs and descriptive authors, explicit orphan status, shared create/update/delete commands, history/dirty/native round trips and bounded UI. No authenticated-author claim.
3. **M3.2 Checkpoints/reference:** immutable non-recursive frozen project snapshots including dictionary/resource context, named catalog, explicit local Reference marker, comparison and atomic restore. At most 20 checkpoints, bounded aggregate payloads, immutable resource sharing, protected reference deletion and schema migration with old-source identity verification.
4. **M3.3 PDF:** user-facing shared-scene vector PDF, bounded A4 pagination and explicit outlined-text fallback. Diagnostics must be acknowledged before writing; existing atomic output and uncertain-outcome handling remain in use. Independently render and inspect representative output; no searchable-text/accessibility claim for outlined text.
5. **M3.4 Complete BPMN modeling/interchange:** the work packages below are required before any 100% claim. They are not collapsed into the presence of element names or preserved XML.
6. **M3.5 Qualification:** full workspace regression, native GUI/CLI/MCP parity, resource/checkpoint performance, external interchange checks and per-capability acceptance artifacts.

Parallel work may cover independent core, interchange, renderer and UI lanes. The coordinator owns integration and qualification. Shared model/command/format files have one writer; API contracts are exchanged before integration. Reuse the current checkout without initializing Git. Never launch Narrator.

## Dependency sequence and slice acceptance

The [crosswalk](../../research/bpmn-2-conformance-gap.md) records the current family-level six-dimension assessment. Its partial cells are bounded profiles, not completion of the family. Update it and the generated inventory when evidence changes; do not treat the declaration inventory as the prose crosswalk.

1. **Definitions, identity and expressions.** Establish typed definitions metadata, namespace-aware references and formal expressions before dependent bindings. Acceptance: new and imported definitions preserve namespace and explicit versus omitted metadata through native save/reopen and BPMN export/reimport; local, external and unresolved QNames retain their namespace identity; expression ID, language, type and XML content survive or are safely preserved/refused. Include positive, negative and no-silent-loss cases and verify existing document identity/migration and undo/redo.
2. **Activities, control flow and events.** Extend task bindings, resources, scopes, loop characteristics, gateway and event contexts on that foundation. Apply Analytic restrictions only to that subclass.
3. **Data, services and collaboration.** Add item-aware and I/O metadata, transformations/assignments, resources, service catalogs, participants, correlations and conversations. Acceptance: identity and references survive scoped native and XML round trips, unknown extensions are preserved or refused without data loss, and each new property has shared commands, UI and CLI/MCP paths with negative reference tests.
4. **Choreography and DI.** Build on the bounded task-band and DI representation checkpoint in `docs/implementation/m3-evidence.md`; implement choreography-owned flows, events, gateways, nested/call/global forms, participants and complete diagram metadata. Acceptance: nested and collapsed cases preserve ownership, all participant bands and visibility metadata; geometry changes keep connected routes and labels; prescribed symbols and hit tests are checked in both themes and exported scenes.
5. **Cross-family qualification.** Complete the clause/table and inheritance mapping and prove all applicable constraints, capabilities and migrations. Acceptance: source and exported fixtures pass pinned XSD checks, semantic positive and negative fixtures pass, native interaction and accessibility checks are recorded, and representative licensed fixtures reopen in two named external tool/version combinations. Record environment-specific gates and results; no absent gate is inferred from a build or test count.

## Comparative product-quality gate

Aim for measurable superiority within the agreed offline modeling/workbench scope, using named SAP Signavio editions and versions as the primary analyst-product benchmark for editor and properties, navigation, library, dictionary, activity table, review, usability, accessibility and productivity. Use Camunda Modeler primarily as an independent BPMN interoperability consumer. Evaluate complete BPMN modeling and interchange, reliability and performance as well. Record reproducible equivalent workflows, fixtures, platform, product editions/versions, settings, metrics and limitations before making any comparative claim. Benchmark complex work and recovery as well as common tasks. This ambition preserves the native local/offline architecture and does not add accounts, a cloud dependency or an execution server. A comparison is not evidence of superiority until measured; M3's normative and qualification gates still apply.

- [ ] Native format tests: V0–V2 digest verification before migration, separate checkpoint payloads, resource deduplication, tamper and expanded-size rejection, Save As requirements, old recovery preservation and unchanged source on failure.

- [ ] Render/export: exact shared geometry/glyphs, all implemented markers, page clipping and bounds, independent PDF raster/outline-policy checks and no external resources/scripts.
- [ ] Native desktop: genuine controls and previews in English Light/Dark, keyboard navigation and 200% scrolling, pending-draft guards, cancellation and late-result rejection. No fake approvals or placeholder success controls.
