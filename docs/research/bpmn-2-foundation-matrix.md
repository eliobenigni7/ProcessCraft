# BPMN 2.0.2 foundation and root-catalog requirements matrix

This working crosswalk covers the foundation, expression and supporting root-catalog constructs below. It is not a claim that the whole standard is mapped. Sources are the pinned OMG PDF (printed page numbers), XSD and CMOF in `tests/fixtures/bpmn20-schema/`; the [declaration inventory](bpmn-2-coverage.json) records source hashes. The PDF's prose and model associations and the XSD's interchange requirements both need review: neither a schema declaration nor source preservation proves semantic support.

**Cells:** P = partial bounded evidence; U = unverified for the complete row; S = unsupported content can be retained as protected source in the documented importer fallback, not editable support; — = no independent diagram glyph is prescribed for the property (its owning element's display remains a separate requirement). P does not cover every attribute, owner, or path. Columns are model, edit/create/delete, render/hit-test, import, export, validate. When a row includes multiple obligations, its P represents only the subset explicitly named in Evidence or gap. Each inherited BaseElement requirement also applies to each descendant, even if a descendant row is otherwise partial.

## Common metadata: prose and XML inheritance boundaries

PDF §8.3.1–8.3.2 Tables 8.5–8.6 describes Documentation as inheriting BaseElement, including ID and documentation associations. The pinned XML schema makes a narrower serialization choice: `tDocumentation` is its own mixed complex type, with optional `id`, `textFormat` (default `text/plain`) and an optional `xs:any` child (default maximum one); it does **not** extend `tBaseElement`. Similarly `tScript` and `tText` are standalone mixed types with optional lax `xs:any`, not generic BaseElement extensions; `tDefinitions` has its own schema declaration despite the PDF's model inheritance. Do not inject arbitrary inherited XML attributes or children into these types on the basis of the conceptual prose alone. Conversely, don't discard their mixed text/child ordering or optional ID/format. XSD acceptance, CMOF modeling and prose semantics require separately evidenced mapping.

`Semantic.xsd:tBaseElement` permits ordered documentation elements, then optional extensionElements and foreign attributes. FlowElement's ordered auditing/monitoring and categoryValueRef QNames are separate; Table 8.44 describes auditing/monitoring as Process-only despite the inherited schema location. Extension `mustUnderstand` defaults false (Table 8.7 and `tExtension`), and an unknown required extension must remain protected or explicitly refused: retaining foreign XML does not mean understanding vendor semantics. Namespaces and QName references retain source context. Full inherited metadata coverage remains unverified across concrete owners.

The source validator's mixed-content boundary also needs explicit qualification. Its current element/reference classification in `crates/processcraft-io/src/bpmn.rs` is driven primarily by expanded namespace and local name, including within mixed or foreign content. Test BPMN-namespaced children embedded in Documentation, script, text and extensions against the pinned XSD and the protected-source policy before applying modeled-owner reference rules; `processContents=lax` may itself recognize global declarations and IDs, so neither universal semantic interpretation nor universal invisibility should be assumed. Existing depth, raw-size, namespace and entity limits remain required. Standard `mustUnderstand` and text-format handling must distinguish explicit unknown semantics from actual supported behavior.
