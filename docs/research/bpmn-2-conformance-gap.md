# BPMN 2.0.2 conformance gap crosswalk

**Status: evidence inventory, not a conformance claim.** This document compares the current implementation with the normative [OMG BPMN 2.0.2 specification](https://www.omg.org/spec/BPMN/2.0.2/PDF) and its [official machine-readable documents](https://www.omg.org/spec/BPMN/2.0.2). Page numbers below are printed specification pages; add 30 for the corresponding PDF page. The [machine inventory](bpmn-2-coverage.json) records individual XSD declarations, source hashes, limited evidence and explicit unknowns. It is not a denominator for conformance: schema validity does not establish graphical, structural, semantic or modeling behavior, and many requirements are prose constraints across elements.

The audited target is complete **Process Modeling** plus **Choreography Modeling**, including visual interchange and preservation of non-executed execution metadata. ProcessCraft does not currently claim any OMG subclass or conformance type. It is not a BPMN process execution engine. Section 2.1 (pp. 1–2) reserves BPMN Complete Conformance for all four types, including process execution and BPEL execution; with execution excluded, calling this target “OMG complete conformance” would be incorrect. Common Executable is a process-modeling subclass for producing executable models, not a claim that this product executes them. Its mandatory modeling languages and supporting metadata still apply if that subclass is claimed (§2.2.2, p. 6).

## Evidence by obligation and next verification

- **Visual syntax — §2.2.3 p. 8; §2.5.3 p. 11.** Verify prescribed glyphs, event/task/loop markers, pool and lane boundaries, message/sequence/association line styles, expanded/collapsed states and hit testing in both themes and exported diagrams. Current renderer tests cover selected families; a per-element reference and actual native inspection are still needed. Size and color flexibility do not authorize changing prescribed shapes.
- **Structural constraints — §2.2.4 p. 8; Tables 7.3–7.4 pp. 40–43.** Test legal and illegal source/target pairs, event/gateway restrictions, message flow between participants, lane and subprocess containment, boundary attachment, branch/default/condition consistency and choreography participants. Core rejects several invalid IDs, cross-scope sequences and attachment references; it does not yet establish every graphical rule. Diagnostics for incomplete work must remain distinct from changes that would corrupt references.
- **Process semantics — §2.2.5 p. 9; Clause 10.** Audit each event definition, activity, gateway, data relation and condition against the element-specific rules. Rendering a tag or accepting schema-valid XML does not prove semantic support. §2.2.5 explicitly says a Process Modeling claim does not require process execution semantics from Clause 13.
- **Required attributes — §2.2.6 p. 9.** Each mandatory field needs an actual create/display/edit path and any prescribed graphical representation. Current typed fields, UI controls, CLI/MCP schemas, history and versioned native storage must be checked together. Unsupported attributes retained only as opaque XML do not count as editable support.
- **Optional and extensions — §2.2.7 p. 9; §8.2 pp. 53–59.** Separate optional support from optional display, and preserve unknown extensions without changing their meaning. Read-only preservation is a safe fallback but is not evidence of the relevant modeling capability.
- **Visual interchange — §2.2.8 p. 9; §2.5.5 p. 11; BPMNDI/DC/DI schemas.** Prove stable IDs, plane ownership, waypoints, labels, expansion, nested scopes and all typed metadata through native save/reopen and BPMN export/reimport. Validate against the pinned XSD and independently reopen a licensed fixture in other qualified tool/version combinations. Existing CLI fixtures in `tests/fixtures/bpmn20-schema/` and `scripts/check_bpmn20_xsd.py` establish only the narrow cases actually checked, not full vendor compatibility.

## Qualification method

For each requirement, record the PDF clause/table and applicable XSD/CMOF declaration, scope and exclusions, implementation path, positive and negative tests, native persistence/undo evidence, GUI and CLI/MCP evidence, DI rendering, fixture provenance and independent round-trip results. Mark a cell **partial** while any required attribute, structural rule or transport remains open; mark **verified** only for the explicitly bounded fixture and evidence. Maintain a second prose-constraint checklist in addition to the schema declaration list. Run pinned schema validation on source and exported files, then test non-schema rules independently. Track execution and BPEL conformance separately as out of scope; do not imply they are met by storing execution metadata.
