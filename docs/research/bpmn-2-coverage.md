# BPMN 2.0.2 coverage baseline

Status: inventory and engineering baseline, not a conformance claim. The authoritative [OMG specification page](https://www.omg.org/spec/BPMN/2.0.2) identifies the normative PDF and the machine-readable 20100501 XSD and CMOF documents. Their exact downloaded bytes and SHA-256 hashes are recorded in [the machine-readable inventory](bpmn-2-coverage.json); source files are in `tests/fixtures/bpmn20-schema/`. Reproduce with `python scripts/generate_bpmn20_inventory.py`.

The inventory enumerates named XSD elements, attributes, types and groups with declaring context, and separately enumerates named CMOF objects and properties. The six columns (model, edit, render, import, export, validate) use `unverified` unless evidence is recorded; the limited profiles marked `partial` include fixture and test pointers: a schema declaration or opaque preservation alone does not prove any capability. The JSON conformance field deliberately remains `not_assessed`. It is not yet an exhaustive mapping of PDF prose, XSD anonymous restrictions, inheritance, or conformance classes; these require a reviewed clause-by-clause crosswalk, normative constraints and fixture evidence before claiming full coverage. Distinguish faithful read-only retention from editable, rendered and validated support. Current source-preservation importer explicitly reports preserved source, and the editable subset is substantially smaller than BPMN 2.0.2.

## Architectural direction

Add versioned typed model families in core: shared BaseElement and references; process activities, events/definitions, gateways, data, resources and expressions; collaboration, participant, message flow and conversations; choreography and choreography tasks; DI shapes, edges, bounds, labels and styles. Model typed fields and cross-references explicitly, preserve execution metadata without running it, and keep extension payloads separately; a workflow engine is outside analyst scope. Scope references by document plus XML ID and validate inheritance, containment, references and diagram ownership. Existing `NodeKind` and `FlowKind` cover only a fraction of this taxonomy and cannot stand in for it.

Define an explicit migration/version boundary before changing the native schema: retain old project readers, validate and migrate old projects transactionally, require safe Save As or backup where existing rules require it, and ensure older readers refuse unsupported required capabilities. Existing commands, history, canonical identity, drafts, recovery, resource ownership and CLI/MCP contracts need typed equivalents and complete digest coverage. Import/export must be bounded, namespace-aware and non-executing, preserve unsupported content without misclassifying it as editable, and refuse destructive writes where round-trip cannot be proved. A supported construct requires explicit create/edit/delete, rendering and hit testing, validation, lossless import/export and undo/redo; DI, labels and style are first-class, not an optional screenshot.

Sequence work by dependencies: (1) base/reference and migration boundary with fixture coverage; (2) activity/event/gateway and execution metadata families; (3) collaboration, conversations and message flows; (4) choreography and corresponding diagrams; (5) full semantic rules and normative conformance crosswalk; (6) independent schema and external-tool round trips for every supported family. Each slice updates its matrix cells only with linked tests and evidence, and proves preservation of unrelated fields. No release may claim 100% until every applicable normative construct and constraint is mapped and independently verified; non-executable metadata support must be distinguished from execution behavior.

For the OMG conformance types, subclass requirements and prose-constraint gaps, see [the conformance crosswalk](bpmn-2-conformance-gap.md).
