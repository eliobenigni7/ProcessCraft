# BPMN semantic and diagram identity/presence audit

The pinned `Semantic.xsd` declares `tBaseElement.id` and `tBaseElementWithMixedContent.id` optional. PDF §8.3.1 Table 8.5 requires an ID when the element is referenced or intended to be referenced and permits omission otherwise. `BPMN20.xsd:tDefinitions.id` is optional. `DI.xsd:DiagramElement.id` and `Diagram.id` are optional, as is `Diagram.name`. XSD reference attributes and their target rules are independent: a required reference needs an addressable target; it does not make every instance of its target class require an ID. Do not confuse internal editor identity, semantic XML ID and representation XML ID, or conflate a missing name with an explicit empty string.

This matrix covers currently modeled families, not all BPMN classes. P is bounded partial support, U means unverified for the full row, S means bounded preserved-source fallback. Columns are model, edit/create/delete, render/hit-test, import, export and validate. Required user interaction, all transports and native migration are not established by a partial cell. A systematic implementation needs stable internal handles independent of optional source XML identifiers and explicit presence for optional names. It must update command/reference resolution, semantic and DI selection, canonical digest, history, checkpoints, recovery, capability negotiation and schema migration together. On export, preserve original absence where permitted; require or allocate an XML identifier only through a deliberate, reviewable rule when a newly created reference requires one, and never silently change unrelated source identity. Old schema identity must be verified before migration. Test omitted versus explicitly empty names, anonymous unreferenced elements, required references, duplicate IDs, semantic/DI ID distinction, native save/reopen and BPMN export/reimport, undo/redo and protected-source fallback across each family. Do not claim support from a per-family boolean or successful XSD validation alone.

The current identity migration introduces internal native selectors independent of optional source XML IDs and optional semantic names. Focused core tests `identity_edit_rewrites_only_typed_local_references`, `promotion_requires_generation_and_targets_only_optional_identity`, `diagnostics_anchor_anonymous_native_elements_without_xml_fallback` and `layout_uses_native_selectors_without_inventing_xml_ids` cover selected mutation, diagnostic and layout paths; the coordinator reports a real MCP promotion/mapping/Undo test passed. ## QName reference resolution and incomplete interchange

BPMN §8.2.1 p. 49 says Definitions defines the visibility scope and namespace of its contained elements. Section 15.3.2 pp. 476–477 states that a QName has an optional namespace prefix and a local part, and that, when it references a BPMN element, the local part is expected to be the element's ID. Its cross-file example uses a prefix bound to the imported namespace; it says IDREF is used where possible and QName where references can span files. Section 15.3.1 pp. 475–476 requires a self-contained set of BPMN files with external definitions imported directly or indirectly.

These passages do **not explicitly settle** whether an unprefixed QName whose XML namespace context expands to the empty namespace must resolve to an element in a Definitions with a nonempty targetNamespace. Section 12.4's bare-ID DI examples are snippets omitting the surrounding semantic model and namespace context. The present qualified profile therefore keeps unresolved no-namespace/local interpretation behind protected-source handling until a lossless reference-context policy and tests establish its meaning. An explicitly foreign namespace URI must never be silently aliased to the local targetNamespace.

In the recorded Camunda Modeler 5.53.0 attempt, a prefixed local DI QName did not resolve in the consumer. A subsequent export used the exact targetNamespace as the local default namespace and an unprefixed lexical QName with the **same expanded QName**; the complete synthetic process then opened visually without import-output entries. This is evidence of a consumer interoperability behavior and a bounded successful alternative, not a finding that the consumer violated the standard or that all bare names denote local targets. See [M3 evidence](../implementation/m3-evidence.md) for the earlier failure, repeat, hashes and limits.

Section 15.1 p. 475 separately addresses incomplete-model interchange and says implementers are expected to disregard attributes marked required and reduce element lower bounds greater than zero when interchanging incomplete BPMN XSD-based models. Event and validator work must account for this distinction between incomplete editing/interchange and structural corruption; an XSD-required field alone is not proof that an incomplete model cannot be exchanged. This rule does not decide QName namespace resolution.
